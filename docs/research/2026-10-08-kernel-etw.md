# Kernel ETW for per-process network and file I/O

- Date: 2026-10-08
- Phase 0 item: ETW ([roadmap](../roadmap.md))
- Machine: the [reference machine](2026-10-06-reference-machine-baseline.md), Windows
  build 26300.9457, on AC, effective power mode "max performance". The measured run was
  started by the owner from an elevated terminal.
- Scope labels as in the [process snapshot note](2026-10-06-process-snapshot-cost.md).

## Questions

1. Does a kernel ETW session need admin?
2. What does consuming per-process network and file events cost, and are events lost?
3. Are bytes attributed to the right process?

Decision rule, written before measuring: accept if, under normal use, the session's
overhead stays below 0.2 % of total CPU and no events are lost at normal rates.

## Method

Throwaway spike outside the repository, `windows-sys` 0.61.2.

- **Session:** one real-time session named `Vagus-Phase0-ETW`, with 64 KB buffers
  (16 to 64 of them) and a one-second flush. It was stopped on every exit path the
  process controls, including Ctrl+C.
- **Providers:**
  - `Microsoft-Windows-Kernel-Network`, with the IPv4 and IPv6 keywords. Send and
    receive events for TCP and UDP carry the process ID and byte count in their payload.
  - `Microsoft-Windows-Kernel-File`, with the read and write keywords. The process
    comes from the event header, the byte count from `IOSize`.
- **Payload fields:** field offsets were resolved once per event schema with
  `TdhGetEventInformation`, not assumed. File names and addresses were never read.
- **Phases:**
  1. 30 s control without ETW;
  2. 30 s with ETW under the machine's normal background activity;
  3. a 1 GiB buffered file write and read, by the spike itself;
  4. 1 GiB of TCP over `127.0.0.1`, between two threads of the spike.

  Each phase ended with a 2-second flush.
- **Measured:** the consumer thread's cycles per phase, converted at the machine's
  2.4 GHz cycle rate; system busy time from per-processor times; events per provider;
  lost events and buffers from `ControlTraceW(QUERY)`; bytes per process.

## Results

### Admin is required (generic)

As a standard user, `StartTraceW` returned `ERROR_ACCESS_DENIED`. The `StartTrace`
documentation says members of the Performance Log Users group may also control trace
sessions. That was not tried: adding the user to the group is a security setting.

### Cost and loss

| Phase | Duration | Events per second | Consumer CPU |
|---|---|---|---|
| Background | 32.0 s | 415 (87 network, 328 file) | 0.42 ms per second |
| File load | 2.7 s | 2467 | 1.23 ms per second |
| Loopback load | 2.3 s | 29188 | 6.61 ms per second |

Lost events: 0. Lost real-time buffers: 0. Buffers written: 799.

At the loopback peak the consumer spent about 0.23 µs per event, including per-process
aggregation in a hash map.

**System-wide overhead could not be resolved.** System busy time was 1218 ms per
second in the control period and 700 ms per second in the ETW background period. The
machine's background activity varies by hundreds of milliseconds per second. ETW's
own cost, which is charged to the threads that perform the I/O, is well inside that
noise.

### Attribution

| Load generated by the spike | Attributed to the spike by ETW |
|---|---|
| 2048 MiB of loopback TCP (1 GiB sent and 1 GiB received) | network: 2048 MiB (100 %) |
| 2048 MiB of file I/O (1 GiB written and 1 GiB read) | file: 1974 MiB (96 %) |

- **Network: exact (generic).** The process ID comes from the event payload, so traffic
  is attributed correctly even though the events are logged outside the sender's
  context.
- **File: 96 %.** The missing part is consistent with cached data being written to disk
  later by the System process.
- **File events are not disk I/O (generic).** During the loopback phase,
  `Kernel-File` also reported 1208 MiB of reads and writes for the spike, because
  sockets are file objects on Windows. `Kernel-File` bytes therefore mix disk files,
  cached I/O, sockets and pipes.
- **Background activity:** a WebView2 process accounted for most file I/O. Two vendor
  lighting services exchanged about 940 KiB each over the network, probably with each
  other.

### Event schemas (generic)

TDH confirmed the layouts used:

- **Kernel-Network:** events 10, 11, 42, 43, 58 and 59 start with `PID` and `size`
  (both 32-bit).
- **Kernel-File:** events 15 and 16 (version 1) carry `IOSize` at byte 36, after
  `ByteOffset`, `Irp`, `FileObject`, `FileKey` and `IssuingThreadId`.

## Verdict

**Accepted for per-process network traffic.** Consumer cost is 0.42 ms of CPU per
second in normal use and 6.6 ms at 29,000 events per second. No events were lost.
Attribution matched the generated traffic exactly. The system-wide part of the
overhead could not be separated from background noise, so that half of the decision
rule is unverified rather than met.

**Not yet accepted for per-process disk I/O.** `Kernel-File` measures file-object I/O,
which includes sockets and cached reads. A disk view needs either disk-level events
(the kernel `DiskIo` events with thread-to-process mapping) or a way to classify file
objects by device without recording file names.

**No change to the privilege model.** Admin is required, so per-process network data
belongs in the Phase 2 `vagus-sensor` service, as
[ADR 0009](../adr/0009-privilege-model.md) already plans. Without it, the daemon still
has per-process I/O transfer counts from the process snapshot, mixed across files and
devices.

## Open

- **Disk attribution:** `DiskIo` events with thread-to-process mapping, or device
  classification of file objects.
- **System-wide overhead:** measure it on a quieter machine or with a longer,
  interleaved run.
- **Real traffic:** network event rates and cost for traffic on a physical network
  interface rather than loopback.
- **Performance Log Users:** whether membership of this group is enough for these
  providers, as a possible alternative to a LocalSystem service.
